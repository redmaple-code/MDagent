# AI 交接方案 —— dsh-agent 硬约束加固（2026-09-17 落地）

> **给接手的 AI（另一台机器上的 Claude / 其他）**：读完本文件你就能接手，不需要原始对话。
> 本次改造把 dsh-agent 从「提示词 + 审计 + 闸门」的软约束体系，改成「内核权限强制」的硬约束体系。
> **读之前先做一件事**：跑 `id`。如果显示 `uid=...(user)`，你在一个**未受约束的老会话**里——
> 立刻告诉用户，并建议用 `run-dsh-jailed` 重启。不要假装约束生效了。

## 0. 三十秒看懂

**改造前**：harness、bash、write/edit、子代理、MCP、看板、审计日志、真相源——全是同一个 uid（user）。
所有闸门（flow-gate / ops-gate / auto-approve）的源码都在 user 可写的目录里。
**唯一真正的硬约束只有一处**：`lmp_mpi` 的 `root:mdorch 0750`。

**改造后**：四个身份，边界由内核强制。

| 角色 | uid | 代码库 | 真相源 | 审计账本 | lmp_mpi |
|---|---|---|---|---|---|
| 人 | `user` | 拥有·可写 | 可写 | 只读 | 经提权 |
| **harness / agent**（bash·write·edit·subagent·MCP） | **`mdagent`** | **只读** | **只读** | **只追加** | **否** |
| 审计执行通道 `claude_interface.py` | `mdorch`（经 sudo） | 只读 | 唯一可写 | 追加 | **是** |
| 看板 / 推送驱动 | `user` | 只读 | 只读 | 只读 | 否 |

**核心性质**：`lmp_mpi` 的唯一可达路径是「agent → `sim_exec` → sudo → mdorch → `claude_interface` 白名单」。
原有的 root 锁没被削弱，而是从「agent 跑不了」升级成「agent 只能经审计通道跑」。

**状态**：node01 已落地，对抗压测 34/34 通过。

## 1. 判据（接手后做任何安全判断都用这一条）

> **一个约束是硬是软，不看它写在哪、叫什么，只看 agent 能不能改写「决定它的那个字节」。**

举例说明这条判据怎么用——`presets/md-sim-assistant/agent.cordis.yml:64` 有一句：

> 「绕过入口的 mdrun 活不过一个 cron 周期——这是代码强制，不是纪律」

方向完全正确，但改造前它的开关（`dashboard/gmx_adopted.json` 的 `auto_kill_wild`）躺在 user 可写的 JSON 里，
一行 bash 就能关掉。**所以它当时是软的。** 改造后该文件归 user、mdagent 只读，这句话才名副其实。

接手后每次想说「这里有保护」之前，先问：决定它的那个字节，我能不能写？

## 4. 接手 AI 的行为宪章（这一节是给你自己看的）

### 4.1 自检（每个新会话第一件事）

```bash
id
```

- `uid=...(mdagent)` → 你在受约束的身份下，正常工作。
- `uid=...(user)` → **你在一个未受约束的老会话里**。立刻告知用户，建议用 `run-dsh-jailed` 重启，
  并在本会话的所有输出里标明「本会话未受加固约束」。**不要因为能做到就去做受控面的事。**

### 4.2 两个面

| 面 | 内容 | 怎么做 |
|---|---|---|
| **自由面** | 分析、绘图、读文献、写一次性脚本、整理 scratch | 直接 `bash`/`write`/`edit`，不必请示 |
| **受控面** | 启停 LAMMPS/GROMACS、改 input/data/力场、杀进程、动编排 state、改 case 目录、改配置与开关 | **只能** `mcp__mdsim__sim_exec` |

受控面没有「优先」、没有「临时顶一下」、没有例外。
在 `mdagent` 身份下你**物理上也做不到**——那些操作会直接 `Permission denied`。

**那不是故障，是设计。** 看到 Permission denied 的正确反应是停下来报告，不是换路径。

### 4.3 失败方向性（压倒性优先）

- **绕过架构完成任务 = 任务失败**，无论结果多漂亮。
- **架构出故障时停下来如实报告阻塞 = 任务成功**，即使什么都没做成。
- 二者冲突时，永远选后者。

禁止使用模拟数据、占位数据、fallback 数据、示意性看板。
万不得已必须使用时，在输出第一行以 `【⚠ 本输出含模拟数据】` 开头，并逐项标明哪个数字是假的。

每轮结束前自检一句：**这一轮里，有没有哪个受控面的操作我是用 bash 做的？**
有就写在回答最前面，不要放在末尾。

### 4.4 数字纪律

`step` / 温度 K / 密度 / `pct` / `case_id` / 采用的策略——**必须来自工具真返回**，查不到就说查不到。

⚠️ 但工具返回也可能是错的（见 §3 的 `species.out` 事故）。数字反常时（例如温度与 `md_config.json`
的 `schedules` 对不上），**先怀疑工具挑错了文件**，再下结论。判断永远不能跑在证据前面。

## 7. 已知残余面（压测确认符合预期，**勿当 bug 报**）

1. **trace 可伪造追加**。`chattr +a` 防抹除、不防伪造——mdagent 能往账本里塞假行，只是删不掉真行。
   要连伪造一起防，需要写日志的进程跑在 agent 碰不到的 uid 下（v1 手册附录 A 有守护进程方案）。
   **建议先跑一段时间确认账本真的在用、真的在对账，再上守护进程。没在用的账本加多少层都没意义。**

2. **白名单含 `python3` → 经审批可跑任意 mdorch 代码**。
   mdagent→mdorch 的墙是**人工弹窗 + 审计留痕**，不是能力零化。
   v1 手册 §1 的表格在这点上会给人虚假安全感，已在 v2 修正。

3. **user 读不了自己的 credentials**（需经 root）。切 uid 的副作用，非缺陷。

4. **`memory/`（atoms.jsonl / LEDGER.jsonl）仍 mdagent 可写**。
   persona 里「不手改账本，走 L2 晋升管线」是纪律不是机制。要硬化：mdorch 独占写 + 经审计通道晋升。

5. **user 本人仍能改一切**。这是设计如此（人是最终所有者），
   但意味着**以 user 身份跑的任何 agent 会绕过全部约束**。
   → **永远用 `run-dsh-jailed` 起 harness，不要图省事跑 `run-dsh.sh`。**
   这是整套方案最容易被自己破坏的一点，也是当前唯一的未完成项（见 §8.1）。

## 8. 未完成项（按优先级）

### 8.1 【最高】替换仍在 user 身份下运行的老会话

`:3091` 的 web 和 tmux 里的 tui 还是改造前起的，**不受任何约束**。

```bash
run-dsh-jailed web --host 127.0.0.1 --port 3091
```

⚠️ **这不只是「覆盖不全」**：老会话的工具调用一条都不会进 `/var/log/mdsim/trace.jsonl`。
所以**在替换之前，账本是不完整的**，§6 的一致性校验会产出**假阴性**——
看板上有的东西在账本里查无此人，但原因是老会话没被记，不是伪造。

**结论：替换之前别把一致性告警当真，也别急着调阈值。** 替换完再看第一批告警才有意义。

### 8.2 验一下 1500 K 那笔旧账

改造前有一个悬着的判断：某 `RUN1500` case 报 `CRITICAL`，温度 `1478.9 K`，
当时的会话判定「大概率是过期快照，不是真爆炸」——**但那是推断，没有核验**。

现在有了新线索：压测时 `RUN2000` 报的是 `1482 K`。两个数字挨得这么近，
而 `md_config.json` 的 `schedules` 里 RUN1500 与 RUN2000 的平台温度差 500 K——真温度不该长这样。

**假设（未验证）**：两次读的都不是温度，而是 `species.out` 的第二列，即 §3 那个已修的解析 bug。
那个 1500 K 的 CRITICAL 可能从来就不是真的，也不是「过期快照」。

验证方法（二选一）：

```bash
# a) 修复后对 RUN1500 重跑巡检，看 CRITICAL 还在不在
# b) 直接看该 case 的 species.out 第二列有没有 1478.9 附近的值
```

⚠️ 在验证完成之前，**不要把这个假设当结论写进任何报告**。
这正是改造前那次失误的形态：判断跑在证据前面。
